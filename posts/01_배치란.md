# 0. 들어가며

은행 프로젝트를 진행하던 중, 데이터 정합성 검증을 위한 일괄 처리 시스템을 구현해야 했습니다.

처음에는 기존 은행 메인 서버에 API를 만들어 작업을 시도했지만, 대량의 데이터를 처리하다 보니 서버 리소스를 지나치게 많이 소모하는 문제가 발생했습니다.   
이를 해결하고자 아예 별도의 스프링 부트 서버로 분리해 보기도 했으나, 하루에 단 한 번 실행되는 작업을 위해 24시간 내내 톰캣(Tomcat) 서버를 띄워두는 것 역시 너무 비효율적이었습니다.

이러한 리소스 낭비와 비효율적인 구조를 어떻게 개선할 수 있을까 대안을 찾던 중 '스프링 배치(Spring Batch)'를 알게 되었습니다.  
이번에 제가 스프링 배치를 처음 접하고 공부하면서 알게 된 내용을 소개하겠습니다.

# 1. 배치가 필요한 이유

은행 시스템을 예로 들어보겠습니다.
은행에서는 매일 자정, 하루 동안 발생한 수백만 건의 결제 및 이체 데이터를 집계하고 정합성을 검증하는 '일일 마감' 작업을 수행해야 합니다.

이 과정을 어떻게 구현해야 할까요?  
저처럼 단순하게 Spring MVC를 활용해 API를 하나 만들고, 이를 호출하는 방식으로 진행하면 다음과 같은 치명적인 문제들을 야기합니다.

1. **서버 자원 독점**: 수백만 건의 데이터를 읽고, 가공하고, DB에 다시 저장하는 과정은 엄청난 CPU와 I/O 자원을 소모합니다. 이 로직이 웹 서버에서 돌아간다면, 해당 서버는 다른 고객들의 실시간 API 요청을 정상적으로 처리하지 못하고 뻗어버릴 것입니다.

2. **비효율성**: 이 마감 작업은 하루에 단 한 번 수행됩니다. 이 단발성 작업을 위해 항상 띄워져 있어야 하는 API 서버의 스레드를 할당하는 것은 심각한 자원 낭비입니다.

3. **실패에 대한 복구(Fault Tolerance)**: 데이터가 워낙 방대하다 보니 네트워크 지연이나 DB 데드락 등으로 중간에 실패할 확률이 존재합니다. 만약 100만 건 중 99만 번째에서 에러가 났을 때, 처음부터 다시 실행해야 한다면 중복된 자료가 생기고 자원이 낭비되게 됩니다.

4. **멱등성(Idempotency) 보장**: 누군가 마감 로직을 실수로 두 번 실행했다면 어떻게 될까요? 고객의 이자가 두 번 입금되는 등의 대참사가 발생할 수 있습니다. 동일한 파라미터(예: '오늘 날짜')로는 이미 성공한 작업을 다시 실행하지 못하도록 막아주는 기능이 필요합니다.

이처럼 사용자와의 상호작용 없이, 정해진 조건(주로 시간)에 따라 대용량의 데이터를 일괄적으로 처리하는 시스템을 **배치 애플리케이션**이라고 부릅니다.

좋은 배치 애플리케이션은 다음과 같은 조건을 만족해야 합니다.

- **대용량 처리**: 방대한 데이터를 읽어오고 가공 및 저장하는 데 최적화되어 있어야 합니다.
- **자동화**: 사용자의 개입 없이 독립적으로 스케줄링되어 실행되어야 합니다.
- **견고성**: 예외 상황이나 유효하지 않은 데이터에 직면하더라도 시스템이 중단되지 않고 적절히 처리(또는 스킵)할 수 있어야 합니다.
- **신뢰성**: 어디서 실패했는지, 무엇이 문제인지 로깅과 추적이 가능해야 합니다.

웹 애플리케이션 개발 시 우리가 Spring MVC 덕분에 비즈니스 로직에만 집중할 수 있듯, 위와 같은 복잡한 배치 조건들을 프레임워크 레벨에서 알아서 처리해 주는 기술이 바로 **Spring Batch**입니다.

# 2. Spring Batch란?

Spring Batch는 Spring 진영에서 제공하는 배치 프레임워크입니다.  
Spring 프레임워크의 기술력(DI, AOP, 서비스 추상화 등)이 결합되어 편하게 배치 시스템을 만들 수 있습니다.

Spring Batch는 기본적으로 데이터를 읽고(Reader), 처리하고(Processor), 쓰는(Writer) 구조로 이루어져 있으며, 다양한 데이터 소스를 기본적으로 지원합니다.

| 분류 | 지원 기술 | 설명 |
|:---|:---|:---|
| Database | JDBC | Paging, Cursor 방식 및 일괄(Batch) 업데이트 완벽 지원 |
| Database | JPA | Paging 지원 및 최신 버전에서는 JPA Cursor 방식도 정식 지원 |
| Database | MyBatis | Spring Batch 공식 지원 커스텀 모듈 활용 가능 |
| File | Flat File | CSV, TXT 등 지정한 구분자(Delimiter) 파싱 지원 |
| File | JSON / XML | JSON 포맷 파싱 및 객체 매핑(Jackson, Gson 등) 지원 |

# 3. Spring Batch vs 스케줄러 (Spring Scheduler)

배치를 처음 접할 때 가장 많이 혼동하는 것이 바로 스케줄러와의 차이점입니다.
"Spring Batch가 있으면 정해진 시간에 알아서 도는 거 아닌가요?"라고 생각하기 쉽지만, 둘의 역할은 명확히 다릅니다.

- **스케줄러 (cron, Spring @Scheduled)**: "언제(When)" 실행할 것인가를 담당합니다. (예: 매일 새벽 2시에 특정 메서드를 실행시켜라)
- **Spring Batch**: "어떻게(How), 얼마나(How much)" 대용량 데이터를 안전하게 처리할 것인가를 담당합니다.

즉, Spring Batch 자체에는 스케줄링 기능이 없습니다.
따라서 실무에서는 보통 스케줄러(Jenkins)가 정해진 시간에 Spring Batch의 Job을 트리거(실행)하는 방식으로 역할을 분리하여 조합합니다.

# 4. 실제 은행/금융권에서의 배치 활용 사례

위에서 언급한 일일 마감 외에도, 백엔드 시스템에서는 무수히 많은 작업이 배치로 이루어집니다.

1. **휴면 계정 전환 및 알림 발송**
   - 지정한 기간 동안 로그인 이력이 없는 수십만 명의 고객 데이터를 조회합니다.
   - 해당 고객들의 상태를 '휴면'으로 일괄 업데이트(Writer)하고, 안내 이메일을 발송(Processor)합니다.

2. **월별 대출 이자 계산 및 청구서 생성**
   - 매월 1일, 대출을 보유한 모든 고객의 이자를 계산합니다.
   - 복잡한 이자율 계산 로직을 거친 후, 각 고객의 청구서 데이터를 생성하여 DB에 적재하거나 청구서 PDF 생성용 메시지 큐로 데이터를 전달합니다.

3. **타 기관 연동 및 파일 송수신 (데이터 파이프라인)**
   - 매일 저녁, 금융결제원이나 외부 신용평가 기관에서 대규모 CSV 파일을 FTP로 전달받습니다.
   - Spring Batch의 `FlatFileItemReader`를 활용해 해당 파일을 안전하게 파싱하고 우리 시스템의 DB에 동기화합니다.
